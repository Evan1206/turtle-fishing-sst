# 方法論:Loop Engineering(構思—執行—驗證分離)工作流

> 本檔案是內部參考用的可複用流程,抽離自「海龜 × 漁船空間關聯」專案的實際執行過程。
> 目標:換一個完全不同的領域(不管是財務報表分析、內容產製、還是另一個資料管線),
> 都能照這套骨架重新組一次。

---

## 1. 核心原則(先懂這個,再看步驟)

> **生成與驗證不能是同一個角色,也不能是同一次思考過程。**

如果同一個 agent(或同一次對話)既寫程式又檢查自己寫的程式,它的盲點會被自己的
盲點覆蓋——它不會發現自己漏掉的東西,因為那正是它沒想到的地方。這套流程的存在
理由,就是刻意製造一個「必須從外部、依照白紙黑字的標準重新檢查」的角色,而且
這個角色**不接受另一方的自我陳述**,只接受可獨立重現的證據。

延伸原則:
- **檔案是橋樑,不是人肉傳話**。任何決策、規格、驗證結果都要寫進 repo 裡的文件,
  不能只存在對話紀錄或口頭交代裡——文件才能被追溯、被下一個接手的人(或 agent)
  讀到完整脈絡。
- **驗證要有停損點**,不是每件事都要停下來問人,但特定類型的決定(見第 5 節)
  一定要停。
- **一次做一個模組,做完就停**。不要讓執行層一口氣做完所有東西才被檢查——
  範圍愈小,問題愈早被抓到,修正成本愈低。

---

## 2. 三個角色與交接協定

| 角色 | 職責 | 不做的事 |
|---|---|---|
| **構思層**(人 + 對話中的 AI) | 定義要做什麼、什麼算對(驗收標準)、判斷資料/結果揭露的意外、拍板架構與假說層級的決定 | 不自己寫執行程式碼(除非經人明確同意的例外情況) |
| **執行層**(生成 AI) | 依規格把工作做出來,讓東西真的能跑 | 不自行更動已鎖定的規格/驗收標準、不自行決定架構性改動、不自行執行對外發布等不可逆動作 |
| **驗證層**(獨立查核者,可以是另一個 AI 或人) | 拿驗收標準逐條核對執行層的產出**是否為真**,結果寫成書面紀錄 | 不寫程式碼、不接受「做完了」的口頭/文字回報作為證據 |

**橋樑 = repo 裡的檔案**,建議至少三份:
- **spec.md**(命令/契約):要做什麼、驗收標準是什麼。任何角色不能自行修改
  已鎖定的驗收標準區塊,要改必須回到構思層討論。
- **CONTEXT.md**(決策理由與陷阱紀錄):為什麼這樣設計、已知容易出錯的地方、
  過去每一次決策的理由。這份文件讓新加入的 agent 不會重蹈覆轍。
- **findings.md / 審查紀錄**(驗證結果):每一次查核的結論,PASS/FAIL 都要附
  證據(哪個值、預期多少、實際多少),不能只寫「看起來沒問題」。

---

## 3. 驗收標準怎麼寫,才是「可執行」的

驗收標準最常見的失敗方式,是寫成主觀形容詞:「做得好看一點」「合理的效能」
「乾淨的程式碼」。這種標準驗證層沒辦法查核,執行層也不知道做到什麼程度算過關。

**做法:把每一條要求拆成 [自動] 或 [人審] 兩類,而且都要可以被明確判定**:

- **[自動]**:能寫成程式斷言的,就寫成斷言(型別、範圍、無重複、欄位存在、
  數值非 NaN、輸出檔案結構符合契約)。這類標準之後可以直接變成自動化測試。
- **[人審]**:無法自動判定、需要人類/獨立查核者的判斷力(視覺印象是否與數據
  方向一致、抽樣資料反推是否正確、因果措辭是否過度、物種/類別是否選對)。
  即使是 [人審],也要寫清楚「查核的具體動作是什麼」,不能只寫「看起來合理」。

**案例(把主觀要求轉成可查核清單)**:當初始需求是「畫面不要太粗糙」「做可愛一點」
這種主觀形容詞時,不要直接照字面去猜,而是拆解成具體、可對照的規則,例如:
「資料代表數值大小的顏色必須維持連續色階,不可用彩虹色階,需經配色驗證工具檢查」
「裝飾元素不可以取代或混淆資料本身的視覺編碼」「圖例必須存在且說明顏色對應的數值區間」。
拆解完之後,審查者只需要逐條打勾,不需要對「好不好看」做主觀评分。

**「已回報完成」不是驗收標準的一種**——這是本方法論最重要的一條紀律。
驗證層永遠要親自確認產出物實際存在、實際可執行、實際符合契約,不能因為
執行層說「做完了」就標記為過關。

## 4. 什麼該自動化,什麼該留人判斷

| 該自動化 | 該留人/獨立查核者判斷 |
|---|---|
| 型別、範圍、必要欄位是否存在 | 資料/內容選得對不對(例如選錯研究對象、選錯資料集) |
| 重複值、缺失值檢查 | 視覺呈現與數據結論方向是否一致(圖表看起來重疊,但報告寫負相關,就是有 bug) |
| 輸出檔案結構是否符合契約 | 抽樣資料人工回推(隨機抽一筆,獨立重新計算,跟系統輸出比對——這是抓「邏輯錯位」唯一可靠的方法) |
| 數值是否為有限值(非 NaN/Inf) | 措辭是否過度(相關不等於因果,統計顯著不等於效應量大) |
| 憑證是否寫死在程式碼裡 | 結果是否與原始假說矛盾(矛盾時是 bug 還是真實反直覺現象,只有人能判斷) |
| — | 實際操作驗證(真的打開瀏覽器、真的跑一次程式,而不是只讀程式碼推斷結果) |

一個好用的判準:**這件事的正確與否,是否需要「懂這個領域在做什麼」的判斷力**?
需要,就留給人或獨立查核者;不需要(純粹是結構/型別/數值範圍),就寫成自動檢查。

---

## 5. 什麼情況一定要停下來問人(不由 agent 自行決定)

- **架構性改動**:改變已經鎖定的核心邏輯模組、改變資料契約的欄位定義。
- **假說/結論層級的意外**:分析結果與原本預期的方向相反,這不是失敗,
  是最需要人判斷的時刻——是 bug 還是真實反直覺現象,不能由執行/驗證層自己
  決定要不要改假說去配合結果。
- **任何對外、不可逆、影響他人可見狀態的動作**:發布到公開網址、對外送出訊息、
  修改共用的基礎設施或權限。這類動作即使技術上已經準備好,也要停下來取得
  明確同意才執行。
- **憑證/敏感資訊相關的處理方式改變**。

**一個實用的折衷模式**:讓執行層做到「本機、可逆」的那一步(例如把變更存成
一筆本機紀錄),但不做到「公開、不可逆」的那一步(例如把變更同步到公開環境)——
中間留一個審查關卡。這樣可以省下大量重複的機械性工作,又不會讓沒被審查過的
東西直接曝光。

---

## 6. 一次查核循環的標準動作(給驗證層用)

1. 讀規格,確認這次要查核的是哪幾條驗收標準。
2. **先確認產出物實際存在**,不要預設執行層的回報是真的。
3. 對照 [自動] 標準逐條檢查(能寫程式驗證的都實際跑一次)。
4. 對照 [人審] 標準,**用獨立於原始程式碼的方式重新推導或實際操作**——
   例如自己手刻一次計算邏輯去對照系統輸出、實際啟動程式/開瀏覽器操作看畫面,
   而不是只讀程式碼判斷「邏輯看起來應該對」。
5. 找到問題時,先判斷這是「執行層該修的」還是「需要回到構思層決定的」。
6. 把查核結論(PASS / 部分 PASS / FAIL)連同具體證據寫進共用文件,
   而不是只在對話裡口頭講一次。
7. 只有在查核通過後,才批准進到下一步或解除某個阻塞條件。

---

## 7. 換到新領域時,要重新填的東西

把這套流程搬到新領域(例如:財報異常偵測、內容審核、客服自動化)時,
需要重新定義的只有:

- 這個領域的「已知陷阱清單」是什麼(對應本專案的經度換算陷阱)。
- 這個領域的「[自動] vs [人審]」驗收標準要寫什麼。
- 這個領域「不可逆、需要人核准」的動作是哪些。

角色分工、檔案交接協定、查核循環的骨架,原封不動照搬即可。
